  1. 01
    Open Docker Desktop.
    Wait until Docker is running.
  2. 02
    Open Containers in Docker Desktop.
    Click ▶ beside your n8n container.
    Start your Gotenberg container too, if used for PDF conversion.
  3. 03
    Open Ollama.
    Press ⌘ + Space, type Ollama, and press Enter.
    It may run without opening a window.
  4. 04
    Open Terminal and check Ollama:
    curl http://localhost:11434/api/tags
    If it returns model information, Ollama is ready.
    If it cannot connect, run:
    ollama serve
    Leave that Terminal window open.
    “Address already in use” means a service is already using that port.
  5. 05
    Open the n8n editor in your browser:
    http://localhost:5678
  6. 06
    Select your AI Incident Briefing workflow.
    Check the Excel file is at the path expected by the Read node.
    Check the HTTP Request node uses your installed model name.
  7. 07
    Click Execute Workflow.
    Wait for execution to finish and check for node errors.
  8. 08
    Open the generated HTML/PDF.
    Compare a few briefing claims against the source records.
  9. 09
    Keep a previous successful HTML/PDF ready as a backup.
    If you show it, explain that it is from a previous run.
Keep Docker and Ollama running throughout the demo.

PROBLEM TO SOLVE

Turn operational incident records into a reviewable executive briefing using a traceable AI-assisted workflow.

WHAT MY WORK DEMONSTRATES

Data scope, human oversight, automated report generation and failure handling.

EVIDENCE & SCOPE

Prototype sampled 15 of 150 records; do not imply production-scale accuracy.

OVERVIEW

I built an AI-assisted workflow that converts structured operational incident data into a concise executive briefing and automatically exports the result as a PDF.

The prototype reads 150 incident records from Excel, selects a 15-record sample for model analysis, generates a structured briefing using a locally hosted Llama 3.2 model, and converts the final output into a shareable PDF report.

THE PROBLEM

Operational incident data can contain recurring patterns, risks, and opportunities for improvement, but reviewing large volumes of records manually is slow and difficult to scale.

The challenge was to design a workflow that could reduce the manual effort required to review incident data and turn selected records into a structured, management-ready briefing.

THE GOAL

Create an end-to-end prototype that could:

01Read structured incident records from Excel
02Prepare a controlled sample for AI analysis
03Send that data to a locally hosted language model
04Generate a concise executive briefing
05Format the result into a readable report
06Automatically export the report as a PDF
DESIGN THINKING → TRADE-OFFS

The decisions behind the experience

These are the design considerations that shaped the solution. They explain intent and trade-offs, rather than claiming outcomes that were not independently measured.

01 · Summarization versus traceability
Separate source incident records from generated interpretations and expose which sample was analysed.

Design implication: Automation versus oversight

02 · Keep review and correction possible before executive distribution; treat model-generated conclusions as proposals, not verified facts.
Prototype scope versus production readiness

Design implication: A 15-record sample from a 150-record sheet demonstrates the pipeline, not representative coverage or validated decision accuracy.

HOW IT WORKS
01Data ingestion

The workflow starts with an Excel file containing 150 structured incident records.

n8n reads the file and extracts the rows into structured data that can be processed by the rest of the workflow.

XLSX Download the datasetreports.xlsx · 150 records ↓
02Prototype sampling

Instead of sending all 150 records to the model at once, I used a Limit node to select 15 records for the prototype.

This gave me a smaller and more controlled input while testing the workflow, model behavior, response structure, and integration.

The workflow reads 150 records and sends a 15-record sample to the AI model during the prototype.
03Data preparation

The selected records are aggregated into a single structured input before being sent to the model.

This makes it easier to pass the incident information together as context for analysis.

04AI integration

n8n sends the prepared data to Ollama using an HTTP POST request.

The request tells Ollama which model to use and includes the prompt and incident data required for the analysis.

CONCEPTUALLY
n8nHTTP request →Ollama API→Llama 3.2→Generated response→n8n
05Local LLM

I used Ollama to run Llama 3.2 locally on my computer.

Ollama

The service that hosts and runs the model.

Llama 3.2

The language model that reads the incident information and generates the briefing.

Running the model locally also allowed me to understand how a local AI service can be connected to an automation workflow through an API.

06Briefing generation

The model is prompted to turn the selected incident data into a short executive-style briefing covering areas such as:

Key findings

Important patterns or recurring signals in the incident data.

Risks

Potential operational concerns identified from the records.

AI opportunities

Areas where automation or AI could potentially support the process.

Next actions

Suggested areas for follow-up or investigation.

The model response is then stored in a clean briefing field inside n8n.

07Report formatting

The generated briefing is transformed into an HTML report using a JavaScript node.

This adds basic structure such as:

01Report title
02Subtitle
03Briefing content
04Consistent typography
05Footer

The result can already be opened as a formatted webpage.

08PDF generation

The generated HTML is converted into a file and sent through a second HTTP integration to a PDF conversion service.

The service returns the final report as a PDF.

THIS COMPLETES THE WORKFLOW
AI-generated briefing→HTML report→PDF conversion→Shareable executive report

DEBUGGING THE INTEGRATION

Several issues appeared while building the workflow.

Invalid JSON formatting

I had to correctly structure the request body before Ollama could process it.

Docker networking

n8n was running inside Docker while Ollama was running on my Mac, so I had to correctly connect the two environments.

Ollama connectivity

The local model server had to be running and reachable before the HTTP request could succeed.

Database/file permissions

I encountered permission issues with the local n8n setup and Docker storage.

Inference timeouts

The model sometimes required more processing time, so request timeout settings had to be adjusted.

PDF request formatting

The final PDF integration required sending the HTML as a binary file using the correct multipart form-data request.

The debugging process taught me to isolate problems one layer at a time instead of treating the workflow as one large system.

PROTOTYPE VS PRODUCTION

This project is a working prototype, not a production deployment.

For production use, I would add:

01Authentication and secret management
02Access controls
03Data classification
04Privacy and security review
05Output-quality evaluation
06Hallucination checks
07Human review for important decisions
08Logging and monitoring
09Error handling and retries
10Governance and approval processes
11Scalability testing
